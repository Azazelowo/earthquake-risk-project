## 第一部分：逐章重點

### 第 1 章 系統分析與設計概念

- **系統開發階段**：系統分析 → 系統設計 → 實作／整合 → 測試 → 上線 → 維運；資訊安全貫穿各階段。
- **表 1-1 系統分析的項目**：現行作業、使用者需求、功能需求、非功能性需求、資料需求。
- **表 1-2 系統設計的內容**：系統架構、軟體設計、資料庫設計、使用者介面、資訊安全、測試方案。
- **表 1-3 系統實施的項目**：實作、整合、測試（單元、整合、系統）、上線、維運。
- **資訊系統類型**：TPS（交易處理，輸入→處理→輸出＋儲存）、MIS（資訊管理）、DSS（資料庫＋模式庫＋互動介面）、ESS（主管支援，結合內外部資料、企業智慧與競爭智慧）、ERP、SCM、Web app、Cloud。
- **資料類型**：結構化（固定欄位、格式、順序）、半結構化（有欄位、不保證一致）、非結構化。
- **整合架構**：資料來源（TPS、POS、ERP、CRM、SCM）→ 資料儲存（DB、資料倉儲、資料超市）→ 資料分析（模式庫）→ 資訊呈現。
- **資訊系統分類架構**：個人、群組、部門、企業、跨組織。
- **系統分析工作（5W1H）**：需求確認問 What、Where、When、Who、How 與 Why；需求分析問「應該做什麼、應該在哪裡、何時開始、由誰、怎麼做」。
- **設計基準**：需求與限制 → 判斷基準。本書的設計產出範圍包括 SRS、初步類別圖、系統循序圖、線框圖、操作合約、互動圖、部署圖、操作手冊、測試報告（OCR 不清，依可辨識的字判讀）。
- **案例**：電子健康紀錄系統失敗、虛擬案例管理系統失敗（需求與專案管理）、軟體錯誤引發的醫療災難。

### 第 2 章 結構化開發模式

- **開發模式的演進**：編碼與修正 → 瀑布 → 結構化 → 雛型 → 漸增 → 螺旋 → 物件導向 → 同步 → RUP → 極限開發（XP）、Scrum。
- **資訊系統生命週期**：啟動規劃 → 設計開發 → 上線 → 維運 → 廢棄汰換。**表 2-1**：每個階段都要做風險評估。例如上線前必須完成風險相關決策；系統環境重大變更時要重新評估；廢棄時要確保資料妥善處理。
- **瀑布模式**：規劃時期（問題定義、可行性分析、需求分析）→ 開發時期（設計、程式、單元測試、整合測試）→ 運行時期（部署上線、教育訓練、維運）。**風險**：問題到後期才會被發現（圖 2-7）。案例：蘇格蘭警察局 i6 系統。
- **漸增模式**：先完成企劃與需求分析，再分組逐一建構子系統（細部設計 → 開發 → 測試 → 部署）。
- **雛型模式**：收集需求 → 建立雛型 → 使用者測試評估 → 修正雛型，反覆循環後再開發、部署、維運。
- **螺旋模式**：擬定目標 → 識別與解決風險 → 發展與測試 → 計畫下一階段；每一圈產生更完整的雛型，**以風險驅動**。
- **同步模式**：讓需求、設計、實作、測試、部署重疊進行，以縮短時程（圖 2-12）。

### 第 3 章 物件導向系統開發模式

- **物件導向程式語言的特性**：物件（屬性＝資料、方法＝行為）、**封裝、繼承、多型**。
- **敏捷開發流程**：專案起始 → 腦力激盪 → 設計 → 開發 → 品質保證 →（下一迭代）→ 所有功能完成 → 部署 → 交付客戶。案例：Spotify 模型。
- **Scrum**：產品待辦清單 → Sprint 計畫會議 → Sprint 待辦清單 → Sprint（1–4 週，每 24 小時開每日站立會議）→ 審查會議 → 回顧會議；以燃盡圖追蹤進度。角色有三種：產品負責人（PO）、Scrum Master（SM）、開發人員。
- **RUP**：迭代式開發。四個階段是初始、細化、建構、移轉；核心流程是商業模式、需求、分析與設計、實作、測試、部署；支援流程是配置與變更管理、專案管理、環境。
- **XP**：使用者故事、驗收測試準則、迭代計畫、簡單設計、重構、結對程式設計、單元測試、持續整合、驗收測試、發布。XP 的一天：站立會議 → 組成雙人小組 → 與使用者對話 → 先寫測試 → 再寫實作 → 重構 → 整合或放棄。

### 第 4 章 統一塑模語言（UML）

- **UML 的發展歷程**：Booch、Rumbaugh（OMT）、Jacobson（OOSE）三種方法合併 → UML 0.8、0.9 → UML 1.0（1997 年 1 月）→ 1997 年 11 月 17 日 OMG 正式採納為塑模語言標準 → 2.x 版。
- **UML 的意義**：統一（Unified）、塑模（Model）、語言（Language）。
- **UML 的組成**：構造區塊（事物、關係、圖）、規則（名稱、範圍、可視性、完整性、執行）、通用機制（規格、修飾、通用劃分、擴充機制）。
- **四類事物**：
  - 結構性：類別、物件、介面（匯入介面畫成依賴、輸出介面畫成實現）、使用案例、合作、元件、節點、主動類別
  - 行為性：互動、狀態機
  - 群組性：套件
  - 註釋性：註解（例如前置、後置條件）
- **擴充機制**：造型（stereotype，例如 «device»、«database»、«interface»）、標籤值（tagged value，例如 `{version="2"}`）、限制（constraint，例如 `{secure}`）。
- **案例**：CMMI 與 UML 的應用。

### 第 5 章 UML 關係

- **完整的關係種類**：抽象、聚合、關聯、綁定、溝通路徑（部署圖的節點之間）、組合、控制流程、依賴、部署、定向關聯、延伸、一般化、介面實現、包含、表現（manifestation）、註解附件、物件流程、實現、使用（usage）。
  - 控制流程和物件流程的差別：物件流程可以攜帶資料或物件，控制流程不行。
- **關聯**：關係名稱、角色名稱、數集（多重性）、方向（雙向或單向）、能見度（`+` 公共、`-` 私有、`#` 保護、`~` 套件）、限定詞（qualifier，用來解決多對多查找的問題）、介面指示器（`角色:介面`）、反身關聯。
- **聚合與組合**：組合的「部分」，生命週期依附於「整體」（實心菱形）；聚合是空心菱形。
- **依賴與關聯的差別**：被當成屬性持有的是關聯；只在方法參數或區域變數中用到的是依賴（圖 5-11 的 Student 例子）。
- **一般化**：用來表達繼承，結構像一棵樹（根類別、葉類別），可以多重繼承（例如 SpaceShuttle 同時繼承 Plane 和 Boat）。
- **實現**：類別實現介面（可多元實現）；使用案例由協作來實現。
- **CRC 卡**：類別（Class）、責任（Responsibility）、合作者（Collaborator），再加上屬性與關係（a-kind-of、has-parts）。附有研究生預約論文討論的使用案例範例，包含主要流程、子流程、替代流程。

### 第 6 章 UML 圖形符號

- **參與者**：一般參與者與商業參與者（«business actor»），參與者之間可以有一般化關係。範例是課務系統（老師、學生、教務處、學務處）。
- **屬性語法**：`能見度 屬性名稱 : 類型 [多重性] = 預設值 {限制}`。**操作語法**：`能見度 操作名稱(參數: 型態, …) : 回傳型態 {限制}`。
- **ECB 樣板（圖 6-8，ECB 對應 VCM 模式）**：
  - 邊界類別 ↔ 展現層（畫面、選單）
  - 控制類別 ↔ 應用（領域）層（商業邏輯）
  - 實體類別 ↔ 資料存取層（負責資料存取）
  - 圖形可以畫成圖示、標籤或裝飾形式。
- **表 6-2 強健型類別之間的關聯**（ECB 類別規則，○＝可以、×＝不可以）：

  | | 參與者 | 實體 | 控制 | 邊界 |
  |---|:-:|:-:|:-:|:-:|
  | 參與者 | ○ | × | × | ○ |
  | 實體 | × | ○ | ○ | × |
  | 控制 | × | ○ | ○ | ○ |
  | 邊界 | ○ | × | ○ | ○ |

  **重點**：參與者只能和邊界互動；實體不能直接和邊界或參與者連；控制可以連實體、控制、邊界。
- **樣板類別**（例如 `Set<T>`）。
- **訊息**：一般訊息、回傳訊息、非同步訊息。
- **介面**：有圖示、標籤（«interface»）、裝飾（棒棒糖）三種畫法；可以多元實現與依賴。
- **套件**：能見度（public、private、protected、package）；匯入用依賴表示，包含用 containment 表示。
- **元件**：有圖示、標籤、裝飾三種畫法；輸出介面（provided）與匯入介面（required）。
- **狀態**：起始、結束、組合狀態、子狀態（互斥或循序、同步）、同步狀態、防衛條件。**移轉**的寫法是 `觸發事件 [防衛條件] / 動作`，另外有自我移轉，以及 `entry/`、`do/` 等內部動作。
- **事件**：事件簽章 `名稱(參數: 類型)`；時間事件（timed-out）、變更事件；訊號用 «Signal» 標示。範例：數位時鐘、電梯升降的狀態機圖。
- **判斷與同步條**：分支與合併（決策節點加上防衛條件）、分岔與會合（同步條）。範例：登入流程、訂單處理。

### 第 8 章 UML 行為塑模視圖

- **使用案例圖**：
  - 元素：系統邊界（主題）、參與者（主角在前台、配角在後台、外部系統）、使用案例、關聯
  - **包含 «include»**：A 必須藉助 B 才能完成功能（例如登入一定要驗證帳號）
  - **延伸 «extend»**：A 自己就能執行，有 B 只是擴充功能（例如付款可以延伸成電子支付或實體支付）
  - 參與者和使用案例都可以一般化（例如精確查詢、模糊查詢是查詢的子使用案例）
- **循序圖**：
  - 元素：框架（sd）、參與者、生命線、控制焦點（執行發生）、訊息標籤、防衛條件
  - 訊息種類：同步（實心箭頭實線）、非同步（開放箭頭）、建立（虛線，«create»）、回應（虛線）、銷毀（«destroy»）
  - **合併片段的互動運算子（表 8-1）**：alt、opt、loop、break、par、strict、seq、critical、ignore、consider、assert、neg。**最常用的四個是 alt、opt、loop、par**。
- **溝通圖**：訊息用編號（1、1.1、1.2…）表示順序，可以加防衛條件（例如 `[學生人數 <= 50]`）。和循序圖表達同一件事，但著重在結構。
- **活動圖**：初始、動作、條件分支、分岔與會合、結束；**泳道**分成直式、橫式。範例是 ATM 提款（客戶、ATM、銀行三條泳道）。

### 第 9 章 專案管理

- **專案和事務性工作的差別**：同時具有暫時性（有明確的起訖日期）和獨特性（和以往不同）的才是專案；只有其中一種是季節性事務，兩種都沒有是例行性事務。
- **PMBOK 第六版**：十大知識領域（範疇、時程、成本、資源、溝通、風險、採購、利害關係人等）和五大流程群組（起始、規劃、執行、監測與控制、結束）。**第七版**：改成 12 項原則（例如注意與關心、團隊、利害關係人、價值、系統思考、領導、量身訂製、複雜性、風險、適應性與彈性、變更管理）和 8 個績效領域（例如團隊、利害關係人、生命週期、計畫、專案工作、交付、績效衡量），再加上量身訂製、模型、方法與工件。
- **WBS**：第一層是專案基礎目標，第二層是相依任務組，第三層是任務。
- **甘特圖範例（數位典藏系統）**：專案啟動 → 需求分析 → 系統分析（確認利害關係人、應用需求調查、非功能需求、建立事件表與使用案例）→ 系統設計（介面、資料庫、雛型、測試資料）→ 程式撰寫（主架構、公用程式、查詢、匯入匯出、單元測試）→ 系統測試 → 安全測試 → 手冊 → 交付。
- **CPM/PERT 網路圖**：工作可以標在箭號上（AOA）或節點內（AON）；節點要標最早開始時間、最遲開始時間。**PERT 期望時間 ＝（樂觀 ＋ 4 × 最可能 ＋ 悲觀）÷ 6**。
- **成本估算**：
  - 參數估算：活動成本 ＝ 工作單位 ÷ 資源生產率
  - 三點估算（三角分布）：（O ＋ M ＋ P）÷ 3
  - 三點估算（β 分布）：（O ＋ 4M ＋ P）÷ 6
- **團隊養成階段**：形成期 → 紛亂期 → 安定期 → 完成期 → 穩定期（對應 Tuckman 模型）。
- 「9-2 角色與責任」「9-5 專案控管與完成」「9-6 數位典藏系統專案規劃」這三節，簡報只有標題頁，內容是口頭講解。

### 第 10 章 專案確認與組織

- **專案成立的五個階段**：專案構想 → 專案立案 → 可行性分析 → 專案人事 → 準備與規劃。審查沒有通過時可以回到構想階段修正。
- **兩種角色**：專案發起人（看見企業需要、爭取資源、處理超出專案經理權限的決策）、專案經理（協調工作、資源與進度，追蹤風險）。**專案起始的時間點**：發起人確定資訊技術能帶來企業價值時。
- **立案的五個核心欄位**：專案發起人、企業需要（為什麼做）、企業需求（系統做什麼）、企業價值（改善了什麼）、特殊議題。
- **可衡量的目標**：要有基準值、量測方式與觀察期間；驗收條件必須能判斷通過或不通過。
- **可行性的四個面向**：技術、經濟（成本效益）、組織（使用者會不會接受）、法律等限制。
- **ROI** ＝（總效益 − 總成本）÷ 總成本 × 100%，總效益與總成本要用同一個評估期間。
- **NPV** ＝ −I₀ ＋ Σ CFₜ ÷ (1＋r)ᵗ；NPV > 0 表示在所採用的折現率下有正的淨現值。**敏感度分析**：改變假設，檢查結論是否會翻轉。
- **專案人事**：發起人、專案經理、分析與開發人員、使用者或業務代表、維運與資安人員。技能不足時可以培訓、委外或尋求內部支援，或經核准後調整範圍。
- **四類標準**：文件標準、表單與報告、程式標準、測試標準。
- **風險與問題**：風險是尚未發生的不確定性，問題是已經發生的狀況。風險又分內部（人員、溝通、流程）與外部（法規、通膨、供應商）。
- **風險評估工具**：SWOT、敏感度分析、機率與影響矩陣（平衡計分卡不列為風險評估工具）。風險清單的欄位：事件、機率／影響、預防或減輕措施、負責角色。

### 第 11 章 系統需求調查

- **需求工程的四個階段**：需求收集 → 需求分析（找出錯誤、矛盾、遺漏）→ 需求描述（產出 SRS）→ 需求驗證（負責人與客戶確認）。
- **五種需求級別**：商業需求、利害關係人需求、功能需求、非功能需求、過渡需求。**最高層次描述「做什麼」，不是「怎麼做」**。參考標準：NASA/SP-2007-6105、INCOSE、ISO/IEC 15288:2008。
- **SRS**：分析的焦點放在「系統目標」的描述上。
- **三種需求分析模型**：
  - 功能模型：產出使用案例模型
  - 邏輯模型（物件、靜態）：產出概念類別圖
  - 程序模型（動態）：產出系統循序圖或溝通圖
- **需求分析基本程序**：事件表、使用案例圖 → 初步類別圖 → 系統循序圖 → SRS。
- **RUP 架構的五種觀點（4+1）**：
  - 使用案例觀點：使用案例圖，**是需求分析第一個要產生的視圖**
  - 邏輯觀點：類別圖、狀態圖
  - 實作觀點：元件圖或套件圖
  - 程序觀點：活動圖、循序圖
  - 部署觀點：部署圖
  - 架構文件稱為 SAD（Software Architecture Document）。
- **需求收集的七個困難**：不同使用者對同一功能的要求不一致、需求經常變動、客戶以為開發者已經懂領域、描述不清、溝通誤解、需求未獲驗證、需求偏離實作。
- **系統化需求收集的三個步驟**：發現領域知識 → 建立現有商業模型（產出使用案例文件與使用案例圖）→ 產生初始需求（產出 SRS）。
- **使用案例塑模的 11 個步驟**：確定範圍與邊界 → 找出參與者 → 找出雙方特徵 → 最上層使用案例 → 分解 → 細化 → 前置條件與結果 → 正常流程 → 例外流程 → 撰寫說明文件 → 畫使用案例圖。
- **找參與者**：主要角色（使用主要功能的人）、次要角色（維護、管理系統的人），以及硬體、外部系統、對結果有興趣的人。
- **利害關係人**：可分為內部與外部（再細分操作、管理、技術三類），或直接與間接。找出利害關係人有四個程序：分析專案文件、腦力激盪、客戶分析、製作表單。
- **RACI 責任分配矩陣**：R 責任者、A 當責者（每個任務只能有一位）、C 事先諮詢者（雙向溝通）、I 事後告知者（單向溝通）。
- **目標受眾**：使用者類型有現有客戶、新客戶、訪客、影響者、外部利害關係人。**STP**：市場區隔、目標市場選擇、產品定位。**人物誌**有六項內容（姓名照片、人口資料、簡介、目標與困難、使用偏好、獲得消息的管道），還要注意四點（使用情境、目標、行為模式、痛點）。
- **需求收集方法**：企業內部以訪談為主（質化），企業外部以問卷為主（量化）。質化方法有訪談、觀察、文件分析、焦點團體、個案研究；量化方法有調查、相關、實驗。
- **競爭力分析**：重要性有三點（了解市場、創新和差異化、避免重複和失敗）。工具有七種：SWOT、BSC、PEST、波特五力、VRIO、7S、BCG。

### 第 12 章 系統需求分析

- **事件的定義**：在特定時間或地點發生、可以描述且值得注意的事情。能列出所有需要系統回應的事件，就能明確知道使用者的需求。
- **三種事件**：
  - **外部事件**：由參與者啟動
  - **暫時事件**（又稱內部事件）：特定時間到了，系統自動處理
  - **狀態事件**：系統內部狀態改變引發，與時間無關，例如安全庫存檢查、資料異常
- **找事件的方法**：依類型、依目標、依服務。**分辨**：固定接續的連續動作視為單一事件；性質相近的動作（例如新增、修改、刪除）合併成一個事件。
- **事件表**：用來找出使用案例。通常一個事件對應一個使用案例，有完整形式和簡單形式兩種。
  - **完整形式的欄位（圖 12-4）**：編號、事件、觸發條件（系統怎麼知道事件發生：外部事件是傳入的資料，暫時事件是事先定義的時間點）、來源（哪一個外部實體）、活動／使用案例（系統執行的作業）、回應（輸出結果）、相關需求、目的地（結果交給哪一個外部實體）。
  - **簡單形式（圖 12-5）**：只有事件敘述與使用案例名稱兩欄。**命名**：事件＝觸發狀態（動詞）＋處理的作業（名詞）；使用案例＝事情（名詞）＋處理方式（動詞）。**六項檢查**：重複或合併、事件與使用案例的對應、是否達成所有利害關係人的目標、是否涵蓋全部功能、是否有遺漏。
- **使用案例**：描述系統行為的動態、劃分系統邊界、是後續視圖的來源。找參與者有七個問題（任務、存取資訊、外部變化通知……）。
- **釐清系統問題的五個面向**：資訊需求、現有問題、互動與流程、性能需求、安全性。
- **描述原則**：清晰明瞭、具體而實用、使用案例分離、需求對應（**不是以使用者介面為中心**）。
- **參與者描述的欄位**：姓名（和圖上完全相同）、別名、輸入資料、輸出資料、描述、註解。
- **使用案例描述的 11 項**：名稱、簡要描述、主要參與者、次要參與者、利害關係人與目標、前置條件、後置利益、觸發、正常情節、例外與替代、補充說明。**事件流程要寫清楚六件事**：何時、如何開始；何時、如何結束；互動關係；需要的資料；主要順序；替代或例外流程。
- **三個關鍵元素**：使用案例、參與者、情節。**三種描述形式**：簡略、中等、詳細（專案初期先簡略，收集需求後再完整描述）。**以系統為黑箱的角度撰寫**。
- **Kenworthy（1997）的撰寫步驟**：確定參與者 → 定義參與者的目標（每個目標是一個使用案例）→ 寫基本流程 → 加入替代流程（延伸）→ 找出共通性（包含）→ 對其他參與者重複。
- **RUP 處理問題的八項原則**：抽象、封裝、繼承、關聯、溝通、組織、比例、行為類型。RUP 物件導向分析的步驟：先確定邏輯模型（類別、物件、結構），再確定程序模型（活動圖、循序圖、溝通圖）。
- **類別塑模的七個步驟**：找名詞（候選概念類別）→ 合併同義詞並排除範圍外的名詞 → 去掉只能當屬性的名詞 → 得到候選類別 → 決定屬性 → 補充動態屬性 → 撰寫分析文件並畫初步類別圖。
- **名詞片語法**（最常用）：名詞對應類別或屬性，形容詞對應屬性，動詞對應操作。
- **程序模型**：擬定情節 → 確定事件 → 準備事件表；可以再畫狀態機圖、活動圖、循序圖、溝通圖。
- **系統循序圖（SSD）**：
  - 四個元素：參與者、`:System`、生命線、框架
  - 繪製原則：操作名稱不要用中文、要考慮參數、回覆是回傳值而不是輸出資料
  - 和循序圖的差別：SSD 是使用案例的延伸，畫的是參與者與系統；循序圖是類別的延伸，畫的是系統內部物件
- **操作合約**：強調「會發生什麼事」，不是「如何完成」。
  - 組成欄位：名稱、責任、類型、參照、註解、例外、輸出、前置條件、後置條件
  - 後置條件的三種分類：物件建立與刪除、屬性變動、關聯形成與移除
  - 撰寫步驟：從 SSD 找出系統操作 → 每個操作一份合約 → 先寫責任 → 再寫後置條件
  - 文件之間的關係：使用案例 → SSD → 系統操作 → 操作合約
- **SRS 的用途**：
  - 客戶：確認是否符合需要
  - 管理者：擬標案、規劃開發
  - 系統工程師：掌握要開發的系統
  - 測試工程師：擬定驗證測試
  - 維護工程師：了解元件之間的關係
- **FURPS+**：功能、易用性、可靠度、效能、支援性，再加上設計、實作、介面、實例四種約束。
- **SRS 格式**：背景說明、系統目標、執行範圍概述（專案範圍與系統運作範圍）、系統架構（部署圖或環境圖）、使用者需求、系統規格（FURPS+，用使用案例與領域模型描述）。
- **SRS 文件建議的七大章（圖 12-23 之後的投影片）**：
  - 壹、說明：目的、文件規範、預期讀者與閱讀建議、產品範圍、專案成員
  - 貳、整體描述：說明、目標、使用者類型特徵、運行環境、限制、軟體品質屬性、假設和依賴
  - 參、外部介面需求：使用者介面、硬體介面、軟體介面、通訊介面
  - 肆、系統特性：系統說明和優先權、觸發與回應順序、功能需求
  - 伍、非功能需求：性能、安全設施、資訊安全、軟體品質屬性、商業運行規則、服務水準、風險規劃
  - 陸、其他需求
  - 柒、附錄：詞彙表、分析模型、待釐清問題列表、參考文獻
- **需求分析作業的完整流程（圖 12-22）**：需求取得（尋找利害關係人、定義事件、事件表）→ 需求描述（使用案例圖、初步類別圖、系統循序圖、操作合約）→ 撰寫 SRS → 可行性分析 → 擬定可行性方案 → 專案管理者確認。
- **SRS 完成之後**：擬定可行性方案（優先次序、自行開發或委外、軟硬體租賃或採購），並和專案經理確認。**產品路線圖**用於策略規劃，順序是環境 → 價值 → 交付 → 信心 → 階段。

## 第六部分：考試重點

以下根據第 10–12 章的隨堂小測題型，以及第 1–9 章投影片的重點整理。

1. **一定會考的分類題**：五種需求級別；三種事件；RE 四個階段；4+1 觀點；三種分析模型和各自的產出；FURPS+；RACI；可行性四個面向；質化五種、量化三種方法；競爭力分析七種工具；UML 14 種圖分成結構與行為。
2. **判斷題**：include 和 extend 的差別；聚合和組合的差別；依賴和關聯的差別；SSD 和循序圖的差別；操作合約描述「會發生什麼」，活動圖描述「怎麼完成」；初步類別圖和設計類別圖的差別；風險和問題的差別；ECB 哪些類別之間可以連線（表 6-2）。
3. **計算題**：ROI、單期折現、NPV、敏感度分析；PERT 期望時間；三點估算。
4. **命名規則**：事件是「觸發狀態（動詞）＋作業（名詞）」；使用案例是「事情（名詞）＋處理方式（動詞）」；SSD 的操作名稱不要用中文。
5. **流程與步驟題**：類別塑模 7 步驟；使用案例塑模 11 步驟；Kenworthy 6 步驟；操作合約 4 個撰寫步驟；系統化需求收集 3 個步驟；專案成立 5 個階段（順序是 D、B、A、E、C）。
6. **符號題**：能見度符號 `+ - # ~`；各種訊息的箭頭；互動運算子 alt、opt、loop、par；狀態移轉的寫法 `事件[防衛]/動作`。
